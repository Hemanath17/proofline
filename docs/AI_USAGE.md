## Tools
- Claude (chat): design partner for the core model, the blueprint diagrams, the build spec and the scenario simulations; also ran the packet queries behind every number in `docs/ERRORS.md`
- ChatGPT: second opinion that criticized the design; several of its points were adopted

## What I decided or corrected
- Required discussion before any design or file; rejected an early switch of the front-end framework
- Pushed for an authentic CPA workflow and judged each idea from the user's side
- Rejected a materiality threshold: any change to an approved value counts
- Challenged area-wide reopening, which led to delta approval
- Challenged carrying approvals over when only the evidence changed, which led to the relied-on-field rule
- Chose Pydantic AI for the investigator and asked for evaluation with DeepEval

## AI mistakes caught
- Wrong roles for staff (corrected against the packet)
- Overstated errors before they were checked
- An AI explanation test showed valid citations alongside unsupported claims in 4 of 10 cases, which is why a person checks meaning

## Measured result
- AI explanations of findings helped in 3 of 10 real cases; not built. Evidence: the ten-case test in the design notes

## Hotfix: every 409 was a bare 500 against real Postgres (Claude Code)
- A real-Postgres check (not this tool's own unit tests, which all share one never-closing session and so couldn't see it) found that every 409 path was raising `DetachedInstanceError` after the request's session closed, turning into a bare 500 -- confirmed directly by experiment which exact step (`session.rollback()`'s expiry, not `session.close()` alone) causes it
- Fixed by making `StaleRevision`/`ActionConflict` carry a plain dict, captured by the raise site while its session was still open, across every raise site in the codebase (`db/repository.py`, `actions/cases.py` x11, `actions/review_notes.py`), not just the two cases that had been reproduced over HTTP
- Added a `closing_client` test fixture (an actually-closing session, unlike the existing shared one) plus a real-Postgres concurrent-race test proving 20 simultaneous responses give 1x200/19x409, never a 500
- Also fixed, in the same pass: a whitespace-only reveal reason was being accepted and saved to the view log (fixed in the one shared `require()` helper, since every required free-text field had the same gap)
- Did not resume the paused Step 5-7 build until told to continue, per the explicit "fix it, then stop" instruction

## Steps 5-7: cases/queue, tracing/documents, areas/sign-off/calculation/disposition (Claude Code)
- Picked up Step 7 (areas, sign-off, calculation, disposition, bulk-verify) where a prior session had left `sign_offs.py` written but unwired; Steps 5 and 6 (cases/queue, tracing/documents) turned out to already be fully built from before the hotfix interruption, just not ticked off in `docs/TODO.md`
- Found, while writing A2's acceptance test against the real packet, that `sign_off` had an unconditional block on any value change that made re-signing a scope after a value changed permanently impossible, contradicting CONTRACTS.md's own "the reviewer approves the change: version n+1 is version n plus that change" -- fixed by removing the block (calling `sign_off` again at the new version *is* the approval) and keeping only the explicit carry-over-confirmation requirement
- Found, by checking which of D30's real dependent lines fall into which C2 scope against the actual packet, that `changes_since_sign_off`'s document-replacement check was unscoped (global), which would have wrongly told scope "business" it needed to confirm a carry-over for a document it never used at all -- directly contradicting A2's own "Business stays signed"
- Ran `/deep-test` focused on the new C2/C3/C4 code and found two more real gaps by reading the fingerprint code against what every call site actually passed it: the "decisions" fingerprint was always computed from an empty list (never wired to real resolved decisions anywhere), and the "scope" fingerprint was computed but never compared -- both fixed, with new tests proving the fix against the real packet's M14 box-move case
- The same `/deep-test` pass also caught a concurrency bug matching the exact same class as the hotfix above: `sign_off`'s own version-numbering had no compare-and-set, so a race on the `(scope, version)` unique index would raise an uncaught `IntegrityError` -- a bare 500 instead of a 409. Fixed and proven with a new pg-marked concurrent test (run three times against real Postgres, no flakiness)
- Verified every new screen (areas list, one area's full S3 page, the RSU case, the SSN case as Marcus, the trace drawer, a document page) by actually running both dev servers against a throwaway local Postgres and taking Playwright screenshots, rather than trusting the component code; caught along the way that Chromium's cached `chromium-1148` build had a corrupted framework and had to fall back to the complete `chromium-1208` build already on disk
- Flagged, rather than silently building, three CONTRACTS.md C2 behaviors that would need real new design work, not a quick fix: `confirm_carryover` doesn't check "source not weaker"/"no judgment on the old document" (no existing notion of source strength anywhere in the codebase), a broken tie-out doesn't automatically open a case, and the large-detail table isn't grouped by issuer/box the way docs/UX.md describes -- all logged in `docs/DECISIONS.md` rather than guessed at
- Ran the `reviewer` agent and it earned its keep: found that `confirm_carryover` validated nothing about the `(old_document_id, new_document_id)` pair it was confirming (the `packet` argument was even accepted but never read -- a tell), that `undo_bulk_verify` could delete a claim's verification set by someone else's later, independent re-verify rather than specifically the event being undone, and that `confirm_disposition`'s lazy first-time row creation had the exact same uncaught-`IntegrityError` race class as the `sign_off` bug found minutes earlier by `/deep-test` -- none of which the acceptance tests happened to exercise. All three fixed, with new tests (including a second pg-marked concurrency test for the disposition race, also run three times with no flakiness)

## Step 8: readiness, the filed-record package, and the post-filing timeline (Claude Code)
- Used the packet-explorer agent twice before writing any code: once for the full Step 8 shape (timeline event names/ids, the exact rejection record and its real path in `tax_agency_records.efile`, the IRS/FTB payment records, the 1099-NEC/1099-K source documents, staff ids, a document's own JSON shape for picking a content-hash approach) and again specifically for `SchC.1`'s engine rule/inputs across all three return versions -- both corrected wrong assumptions before they became code: the rejection's real path is `/tax_agency_records/efile/0`, not an id-addressable record, the California submission is a separate `not_transmitted`/`STATE-HOLD` entry rather than a second rejection, and `SchC.1` has `rule="R-SCHC-GROSS"` with no `inputs` at all (not an R-SUM chain), which ruled out the propagation-through-sums approach I'd initially assumed and led directly to the narrow `resolved_line_value` workaround instead
- Found, by actually computing the new "estimated payments agreed" tie-out against the real packet rather than assuming it would pass, that it doesn't: the engine's declared federal estimated payments (13,000, resting partly on a questionnaire "I think" answer for a January payment) disagree with the IRS transcript's four posted 670 entries (12,000), and the California figure (14,000) disagrees with the FTB account's own tax-year-2025-designated payments (10,500, since the engine's date-range rule pulls in a payment the FTB itself designates tax year 2024). Neither discrepancy is in `docs/ERRORS.md` yet -- they're new leads this readiness check surfaces, not confirmed errors, and nothing was hardcoded to make the check "pass"; it correctly reports "not ready" for a real reason
- Worked out from first principles, before writing `submit_filing`, that enforcing "the submitted package reference must equal the most recently authorized one" is the single generic rule that satisfies both halves of CONTRACTS.md's resolved "still open" question (identity changes needing a new signature, no threshold, *and* the pre-existing "even $2 is $2" amounts rule) without writing separate code paths for which fingerprint changed -- proven directly in `test_a3_efile_rejection.py` by confirming F1's reference is refused once F2 exists
- Deliberately chose not to widen `calculation.line_claim_identity` to make `SchC.1`'s E3 adjustment generically resolvable (which would have been the "more correct-looking" fix), after tracing through that doing so would also silently make every other line in the return independently verifiable via `bulk_verify` and show a "verify" control on every area-detail row -- a much larger behavior change than this step asked for, with no test coverage for those wider consequences. Took the narrower, locally-scoped function instead and wrote down the tradeoff in `docs/DECISIONS.md` rather than picking silently
- Attempted to start a local throwaway Postgres (the same approach a prior session used, at a different port) to actually run the new `filed_records` immutability test against a real database; the sandbox denied starting the daemon process. Did not retry or route around the denial -- logged the gap in `docs/TODO.md`/`docs/DECISIONS.md` the same way the still-missing `TEST_DATABASE_URL` was logged at the end of Step 7, rather than quietly skipping it
- Reused, rather than re-derived, three pieces of evidence already established as real work in this codebase: `compute_fingerprints` (Step 7) for the package's amounts fingerprint, the `return_total`/`household_fact` claim-identity helpers (already defined, just not yet wired to a household field) for the identity fingerprint, and the exact reveal-and-log pattern from `routes/documents.py` for showing a cleared actor the e-file PINs
- Brought line coverage on the six new modules to 99% (one deliberately-untested defensive branch, matching the project's own precedent for `get_engine()`'s real-DB-only branch), closing several real gaps found by reading the coverage report rather than stopping at "the acceptance test passes": the readiness report's open-cases/open-notes/pending-carryover branches, the Letter 566 pack's two text-parsing fallback paths, and `authorize_filing`'s two early validation guards all had no test until the coverage run pointed at them by line number
- Found, while running `/deep-test`'s own edge-case pass before the reviewer agent did, that calling `submit_filing("accepted")` twice in a row for the same jurisdiction would silently write a second `FiledRecord` -- nothing enforced CONTRACTS.md I6's "written once." Fixed with an explicit check plus a unique index on `filed_records.jurisdiction` (amendments aren't built yet, so exactly one per jurisdiction is correct for this step) and the matching `IntegrityError`-to-`ActionConflict` handling the same race class already needed twice in Step 7
- Ran the `reviewer` agent against the whole diff and it found three real issues I'd missed, each verified with its own reproduction rather than taken on faith: a PIN recorded through `authorize_filing` leaks unmasked to an uncleared actor whenever it doesn't happen to already appear in the packet's own timeline text (my PIN-masking design had quietly assumed every PIN this system would ever record *was* already in the packet, which is only true for this one client); `analysis/readiness.py`'s pending-change check never compared the decisions fingerprint, so a scope could read "no pending change" even after a case was resolved into an adjustment since it was last signed; and `build_package`'s own package lines didn't get the same SchC.1 adjustment-awareness I'd written specifically for the Letter 566 pack, so the two could disagree about the same line's value. All three fixed, with regression tests reproducing each one (a PIN that appears nowhere else in the packet; a decision-only change with no engine-side value change; a direct comparison between the package's line and the Letter 566 pack's reconciliation for the same adjusted claim). Fixing the second one required consolidating a function (`resolved_decision_ids_in_scope`) that had been duplicated once already out of `actions/` and into `analysis/signoff.py`, rather than duplicating it a third time

- Planned the whole step into `docs/TODO.md` before writing any code, as asked, then sent one combined packet-explorer query covering every fact the step needed (budget-hours keys, the firm's assignment/deadline/variance-rule shapes, exactly where the four outside-filing items and the Form 8867 checklist do or don't live, the books-to-tax and K-1 and retirement/foreign source documents, every prior-year basis gap) rather than one query per record view -- one round trip instead of sixteen
- The packet-explorer research directly reshaped three parts of the plan before any code existed: `firm.assignment_at_start` turned out to be a flat role->staff-id dict, not per-scope as I'd assumed going in; the Form 8867 checklist doesn't exist anywhere in the packet as structured items (only firm rule text and one status line), so R-G's checklist had to surface what's actually there instead of inventing item names; and R16's "prior preparer vs. what we changed" has no line-level prior-year data to diff at all, so it compares open items against judgments/outside-filing decisions by word overlap instead of forcing the version-diff shape onto data that isn't shaped like that
- Decided up front, and confirmed true throughout the build, that nothing in this step needed a new database table or an Alembic migration -- time entries, judgments/elections and outside-filing decisions are all append-only facts, modeled as log-only events read back by replay, the same shape Step 8's `confirm_readiness_item` already established. Caught one real gap the same read of the packet surfaced: `Asset.disposition` (the Form 4797 recapture detail for the condo sale) had been silently dropped by Pydantic the whole time, since nothing had ever added the field to the model
- Retrofitted a permission guard (`require_non_client`) onto eight pre-existing staff-surface route files rather than leaving the client workspace as an addition on top of an already-open API -- every one of those routes was previously reachable by a client actor, with only sensitive values masked, which is the opposite of "a genuinely smaller API surface" the step asked for. Updated the existing leak-scan test to prove the client now gets a clean 403 (a stronger guarantee than the masked-200 it used to get), rather than quietly weakening that test to stop checking the client row
- Chose one generic recursive renderer for the sixteen CPA record views instead of sixteen bespoke table layouts, after noticing the sixteen responses are genuinely heterogeneous in shape (some are flat row lists, some are nested objects, some are both) but all read-only -- the UX spec's own "detail tables are read-only views" principle covers a generic renderer just as well as sixteen custom ones, for a fraction of the code
- Verified the whole step against a live `uvicorn` process with its database session overridden to an in-memory SQLite engine, rather than the real demo database or a fresh local Postgres -- starting a local Postgres daemon was denied by the sandbox again (same as Steps 7-8), and writing this step's test data (time entries, judgments, outside-filing decisions) into the shared demo database would have left permanent, undeletable events there for data that exists only to prove a screen renders
- Ran the full backend test suite twice (607 passed, 13 skipped, no flakiness) and both frontend `typecheck`/`lint` clean before calling any part of this done
