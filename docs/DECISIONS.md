# Decisions

| Date | Decision | Why |
|---|---|---|
| 2026-10-17 | Next.js + FastAPI + Neon on Vercel, free tier | One project, Python for the domain logic, no cost |
| 2026-10-17 | Three kinds of information: packet, analysis, actions | Facts never change; analysis stays fresh; decisions are kept |
| 2026-10-17 | Current-state tables written in the same transaction as events | Fast reads and easy debugging; events stay the audit history; state can be rebuilt |
| 2026-10-17 | Check runs saved at each decision | Proves what a person saw even after code changes |
| 2026-10-17 | Cases for investigation, areas for approval | One place to work, one place to prove completeness |
| 2026-10-17 | One root cause opens one case | Prevents alert fatigue |
| 2026-10-17 | No per-number workflow states; verification recorded per claim, done in bulk for tied groups | Avoids clicking through 3,000 values while still recording how each was verified |
| 2026-10-17 | Provenance resolver as a central component | Powers tracing and targeted invalidation |
| 2026-10-17 | Claim identity by item, not line key | Lot M14 moved from box A to box D in the corrected 1099 |
| 2026-10-17 | No materiality threshold; any change to an approved value counts | A program should not decide a change is too small for a CPA |
| 2026-10-17 | Approve the change, not the area again (delta approval) | Re-reviewing 299 unchanged lots adds no assurance |
| 2026-10-17 | Carry-over only when every relied-on field is identical, confirmed once per replaced document | A same result can hide offsetting changes |
| 2026-10-17 | Four sign-off fingerprints and a Tax computation scope | Return-wide totals would otherwise reopen unrelated areas |
| 2026-10-17 | Typed conflict resolution, no plain Accept; evidence required per resolution type | Stops disagreements disappearing and confirmation bias |
| 2026-10-17 | Awaiting-partner state for effects over 1,000 | Firm rule |
| 2026-10-17 | Green means "approved for a version", never "correct" | Agreement is not correctness |
| 2026-10-17 | Exact only along R-SUM and R-CARRY and packet what-ifs; otherwise estimate | The engine cannot be rerun |
| 2026-10-17 | Readiness evaluator separate from cases | Zero open cases is not enough to file |
| 2026-10-17 | Packages, client authorization bound to fingerprints, immutable filed record | The accepted return can be rebuilt years later |
| 2026-10-17 | Never the raw packet in the browser; redaction inside document text | Documents print SSNs |
| 2026-10-17 | Client approval workspace, not only questions | The brief requires approval, signature and a filed copy |
| 2026-10-17 | AI explanations of findings not built | Helped in 3 of 10 tested cases; fixed wording was as good |
| 2026-10-17 | One Pydantic AI Evidence Investigator under an AI-assistant role | Tool calling and typed output; permissions enforced by the role |
| 2026-10-17 | DeepEval with hard gates, judge checked against hand labels | Measured value, not demos |
| 2026-10-17 | Langfuse for redacted traces; AI provenance in our own events | Debugging versus audit record |
| 2026-10-17 | MCP server for the same tools, after the core | Outside agents get exactly the AI-assistant permissions |
| 2026-10-17 | Not used: embeddings and pgvector, DSPy, multi-agent frameworks, anomaly models, open Q&A, fine-tuning | Each fails a stated need; see the Blueprint |
| 2026-10-17 | Tax wording: review, sign-off, IRS examination | This is tax compliance work, not auditing |
| 2026-10-18 | Vercel Services (one project, `web/` + `api/`) worked as documented; no fallback to two projects needed | `vercel link` auto-detected and connected the GitHub repo, and both services deployed and routed correctly on the first try |
| 2026-10-18 | Cold-start measured at ~336ms for the first `/api/health` request on a fresh production deployment (vs. ~289ms on the next request) | Fluid Compute pre-warming keeps cold start close to warm; no action needed at this step |
| 2026-10-18 | Added `python-dotenv` to `api/requirements.txt` | Local `uvicorn` and `alembic` runs need `.env.local` loaded manually; Vercel injects env vars directly in production so this is dev-only |
| 2026-10-18 | A 1099-B lot's claim identity is issuer + lot id (falling back to issuer + security + acquired + sold + quantity), not issuer + account + lot id | The packet has no structured per-document account field; account numbers, where printed at all, are inside free-text `printed_content`. A same-issuer correction still keeps the same identity across a box move, which is the behavior CONTRACTS.md cares about |
| 2026-10-18 | A line's "excluded" documents (e.g. D10 relative to D09 for F1040.1a) are found by data, not by id: same issuer + same document type as a primary source, contributing zero extracted values to any line in that return version | Avoids hardcoding a specific document id while still satisfying the Step 2 Done criterion; full document disposition (used/duplicate of/superseded by) is still Step 7, this is only the provenance layer surfacing what the packet's own `sources` already say |
| 2026-10-18 | Checks read `packet.return_versions[-1]` as "the current version" rather than the literal string `"v3"` | Keeps every check working unchanged once a v4 exists, without any code change |
| 2026-10-18 | `TaxEffect.direction` is `"overstated"` or `"understated"`, describing the effect on tax as currently reported, not on income or basis | A reader of a finding wants to know which way the return is wrong, not which underlying number moved |
| 2026-10-18 | The baseline (`baseline.py` + `baseline_expectations.json`) counts a finding as confirming an error only when evidence or claims overlap, not on `check_id` alone | A later bug fix inside a check module could produce an unrelated finding that happens to share a `check_id` with a confirmed error; matching on `check_id` alone would hide that regression by reporting it as "found" |
| 2026-10-18 | `events.seq` is a Postgres identity column, `NOT NULL`, with `repository.insert_event()` assigning a placeholder (`0`) only when the session's dialect is `sqlite` | Postgres requires an identity column to be `NOT NULL` and rejects dropping that constraint afterwards (confirmed against the real database); SQLite (used only by the fast in-memory test fixtures) has no equivalent generation mechanism, so it needs *some* value supplied. Production never takes the sqlite branch, so Postgres's real sequence always assigns the value there |
| 2026-10-18 | `baseline_expectations.json` stays in `api/fixtures/` (excluded from the Vercel function bundle) and `baseline.py` stays dev-only, documented as such in `CLAUDE.md`, rather than relocating the fixture | Nothing in `proofline/app.py` or `routes/` imports `baseline.py` -- only tests and its own `__main__` block do -- so it was already dev-only in practice; moving the fixture would be a bigger change for no behavior difference |
| 2026-10-18 | `proofline/provenance/tracing.py` caches "documents used by any line" on the `ReturnVersion` object itself (a private attribute, populated lazily on first use) rather than in a module-level dict | A module-level cache keyed by `id(packet)`/`id(rv)` risks a stale hit after Python reuses a garbage-collected object's id across unrelated test packets; caching on the object instance lives and dies with it, so there's nothing to invalidate |
| 2026-10-18 | `/api/health`'s 503 body says only `"database unreachable"`; the real driver exception is logged server-side (`logger.error(..., exc_info=exc)`), never returned | The endpoint is unauthenticated; a driver's exception text can carry a hostname, database name or file path |
| 2026-10-18 | Moved the actual `SELECT 1` call into `proofline/db/connection.py` (`check_connection(engine)`); `routes/health.py` calls that instead of importing `sqlalchemy` and executing SQL itself | CONTRACTS.md's Storage section says `proofline/db/` is the only code that touches the database; the first version of the health check broke that by executing raw SQL from `routes/` |
| 2026-10-18 | The sqlite/seq placeholder is a named, directly-unit-tested function (`repository._needs_sqlite_seq_placeholder`), not an inline dialect check | Lets a test assert the gate is `True` only for `"sqlite"` and `False` for `"postgresql"` without a network connection (both engines are constructed, never connected to), rather than trusting the inline condition by inspection |
| 2026-10-18 | `runner._run_module` materializes a check's findings into a plain list and checks every item's type *before* any of them are added to `CheckRunResult.findings` | A check that returns a generator raising partway through, or the wrong type, could otherwise leave partial or malformed findings in the result while also being recorded as a `CheckFailure` for the same check |
| 2026-10-18 | `api/index.py`'s unused-looking import is enforced at the config level (`pyproject.toml`'s `[tool.ruff.lint.per-file-ignores]`), not just an inline `# noqa` | An inline `# noqa: F401` alone didn't stop `ruff --fix` from deleting the import once already (it's the file's entire content, so "unused" always looks true) -- the per-file-ignore stops ruff from ever flagging it, so there's nothing for `--fix` to act on |
| 2026-10-18 | `DEPENDENT_SSN_INDEPENDENT_SOURCE` groups every disagreeing independent source for one person into a single finding, rather than one finding per disagreeing document | A typo on a person with three W-2s is one wrong SSN, not three separate findings about it; evidence_refs lists every disagreeing source so nothing is lost |
| 2026-10-18 | A prior-year dependent entry that matches by name but has no recorded `"ssn"` is treated as if there were no prior-year entry at all, not compared as if the blank meant anything | `_digits_only(None)` crashing the whole check (losing every other person's real finding too) is worse than just skipping a comparison that can't be made |
| 2026-10-18 | `RSU_LOT_ZERO_BASIS_SUPPLEMENT_AVAILABLE` matches a lot to a supplement by checking every one of the supplement issuer's *distinctive* words (stopping at the first corporate suffix or generic/descriptive word) against the lot's description, or by ticker/CUSIP when the packet has one -- not by any shared word | Two unrelated issuers sharing one generic word (both named "... Systems ...", "... Group", etc.) previously matched and inflated a confirmed error's tax effect by pulling in an unrelated lot |
| 2026-10-18 | A lot's `covered` flag that can't be read as a clear yes/no (`parse_bool` returns `None`) is reported as a `possible_discrepancy`, not silently treated as covered | `if value:` on the string `"false"` is `True` -- the extraction pipeline printing a boolean as text was silently hiding exactly the lots this check exists to find |
| 2026-10-18 | `parse_money` rejects `bool` explicitly, before the `int`/`float` branch | `bool` is a subclass of `int` in Python, so `True`/`False` would otherwise reach `Decimal(str(value))` and raise `decimal.InvalidOperation` instead of the `ValueError` every other invalid value raises |
| 2026-10-18 | `tracing._documents_used_by_any_line`'s whole-return-version sweep uses a new `_documents_for_line_lenient` that skips a *dangling ref*, not a whole line, instead of letting one bad ref anywhere propagate | That sweep only exists to detect excluded-duplicate documents across the *whole* return version -- one bad ref shouldn't make every other line's own trace fail too, and a line with one bad ref among several shouldn't also lose its *other*, resolvable sources from the sweep. The reviewer agent's first pass flagged the original per-line version as a real (if low-risk) precision gap; made per-ref instead. The line actually being traced still raises on its own dangling ref, via the strict `_documents_for_line` called directly from `trace_line` |
| 2026-10-18 | `tracing.trace_document` also uses `_documents_for_line_lenient` while checking which lines use a document, instead of the strict version | Caught by `/deep-test`: `trace_document` has its own independent whole-return-version loop over every line's sources, with the identical blast radius -- a dangling ref anywhere was still breaking tracing for an unrelated document |
| 2026-10-18 | `/api/health` and every other route now go through one app-level exception handler (`app.py`, for `DatabaseUnavailable` and SQLAlchemy's `OperationalError`) that returns 503 "database unreachable" | `get_engine()` raising a missing-`DATABASE_URL` error happens while FastAPI resolves `Depends(get_engine)`, before a route's own try/except runs -- `/api/health`'s local catch couldn't reach it, and no other route (e.g. `/api/events`) had any protection at all, so both were coming back as a bare 500 |
| 2026-10-18 | `get_database_url()` raises a new `DatabaseUnavailable` (in `db/connection.py`) instead of a bare `KeyError` when `DATABASE_URL` is missing | Gives the app-level handler above one specific, intentional exception type to catch for the "not configured" case, rather than catching `KeyError` broadly (which could mask an unrelated bug elsewhere) |
| 2026-10-18 | The `seq` backfill in migration `41f2af2e559e` followed Postgres's identity sequence in storage order, not `created_at` | Acceptable only because the table held nothing but the Step 1 proof-of-deploy rows at the time, where storage order and creation order happened to match. Any future backfill of an ordering column onto existing rows must explicitly order by `(created_at, id)`, not rely on whatever order the database already stored them in |
| 2026-10-18 | Clients and the AI assistant never get `clearance` in Step 4; redaction is a staff-only concept until Step 9 | User's call: matches `/simulate`'s leak-scan scenario, which groups Marcus, the client and the AI assistant together as the three actors who must never see an unmasked sensitive value. A client's own unmasked view of their own data is deferred to the client workspace |
| 2026-10-18 | Review notes follow real practice, not a simplified stand-in: only reviewer/partner/quality_reviewer may raise one (`add_review_note`); any staff member may respond (`respond_review_note`, new action not in the original Step 4 list); only the note's own author or the partner may resolve it (`resolve_review_note`) | User's call, given explicitly in place of the simpler "any staff resolves any note" default. The 403 for a non-author, non-partner resolve attempt ("only the reviewer who raised a note, or the partner, may clear it") is acceptance test I3's example |
| 2026-10-18 | A review note's thread of responses lives only in events (`review_note_responded`), never as rows on the `review_notes` table; `respond_review_note` only bumps the note's `revision` | A growing log of what people said is "what people did", not a point-in-time snapshot -- same three-kinds-of-information split the rest of the design already uses. `revision` still serializes concurrent responders even though the response text itself isn't in the current-state row |
| 2026-10-18 | `reveal_sensitive_value` is log-only: no current-state row, no revision check | There's nothing to version -- revealing a value doesn't go stale the way an edit does. The event itself is the view-log entry CONTRACTS.md Redaction asks for |
| 2026-10-18 | `apply_revision_cas` (proofline/db/repository.py) uses a single `UPDATE ... WHERE id = :id AND revision = :expected` with `synchronize_session=False`, then `session.refresh()` the row, rather than trusting SQLAlchemy's "evaluate" sync strategy | Confirmed by hand that "evaluate" can silently sync some columns of a multi-column `SET` onto an already-loaded object in the session but not others (`status` synced, `resolved_by` didn't, in the same statement) -- refreshing from the database is the only reliable way to get the post-update row back |
| 2026-10-18 | `ReviewNote.to_dict()` normalizes a naive `opened_at`/`resolved_at` to UTC before calling `.isoformat()`, rather than comparing raw `datetime` objects | SQLite's `DateTime(timezone=True)` type doesn't reliably round-trip whether a stored timestamp was timezone-aware -- the same value could come back naive or aware depending on whether it was freshly loaded from the database or still the original in-memory object. This only matters for the offline SQLite tests (I5, I7); a real Postgres `timestamptz` column doesn't have this problem |
| 2026-10-18 | The `client` test fixture (`api/tests/unit/conftest.py`) builds its SQLite engine with `StaticPool` and `check_same_thread=False` | `TestClient` dispatches each HTTP request on its own worker thread, and a plain `sqlite:///:memory:` engine hands a brand-new, empty in-memory database to each new connection/thread -- without `StaticPool` forcing every checkout onto the one connection the fixture created, the tables `Base.metadata.create_all()` just created would be invisible to the request thread |
| 2026-10-18 | `proofline/db/connection.py`'s `get_session()` now commits only if nothing raised and rolls back otherwise, instead of never managing the transaction itself | The action service's "one transaction, nothing partial on failure" (I1) has to be enforced somewhere that wraps the whole request, not inside `insert_event` (which now only flushes, never commits, since it may be one of several writes in the same action) |
| 2026-10-18 | The three new Step 4 migrations (`7e12e0496083`, `b4c6bbd57994`, `60f9607200ec`) and the edited `downgrade()` on `8a1aa2459a26` were verified end to end -- `upgrade head`, `downgrade` back to the pre-Step-4 schema, `upgrade head` again, `alembic check` -- against a throwaway local Postgres (started and torn down for this check only), never against the demo `DATABASE_URL` | CLAUDE.md: don't run migrations against the demo database without separate OK, but a migration that's never been proven against real Postgres isn't trustworthy either. `alembic check` reported no drift between `proofline/db/models.py` and the applied migrations |
| 2026-10-18 | `ReviewNote.__table_args__` now explicitly declares `Index("ix_review_notes_about", "about_type", "about_id")` | Found by `alembic check` against the local Postgres above: the migration created this index but the SQLAlchemy model didn't declare it, which `alembic check` correctly read as undocumented drift -- a real model/migration mismatch, not a false positive |
| 2026-10-18 | `/deep-test` added 8 tests closing real coverage gaps (`get_session()`'s actual commit/rollback path, the `EntityNotFound`/`ActionValidationError` HTTP-level exception handlers, four 404 paths, `trace_line`'s `UnresolvedReferenceError` to 422 mapping -- which never fires on the real packet since every reference already resolves, `perform()`'s defensive guards for a direct (non-route) caller, `resolve_review_note`'s own unknown-note check, the `about_type`/`about_id` filter on `list_review_notes`, and two small edge cases in `actors.py`/`redact.py`) | No production code changed for any of these -- every gap was a real, previously-unexercised code path, not a reason to rewrite the code to be more "testable" |
| 2026-10-18 | ~~`respond_review_note` doesn't block responding to an already-resolved note~~ -- **superseded below**, same day | Originally accepted as-is per the reviewer agent's finding (nothing in CONTRACTS.md requires it), but reconsidered and reversed once the question was asked directly |
| 2026-10-18 | No endpoint reads a review note's own text back (its `body` lives only in events) | Reviewer-agent finding, accepted as a known gap for Step 5 to close when it builds the actual case screens -- Step 4 has no screen that would use it yet |
| 2026-10-18 | `reveal_sensitive_value` now requires a `reason` (saved on the `sensitive_value_revealed` event), the same way a review note's `body`/`resolution` is required | User's call: a view-log entry that only says *what* was revealed and not *why* isn't a usable audit trail. `require()` (the "missing or blank raises `ActionValidationError`" helper) moved from `review_notes.py` to `actions/errors.py` so `reveal.py` could share it rather than duplicate it, now that two modules need it |
| 2026-10-18 | The document-page route's own automatic reveal (when a cleared actor's page actually contains a sensitive value) supplies a fixed, generated reason -- `"viewing document {id} page {n}"` -- rather than prompting for one | That reveal isn't a deliberate action a person took; it's a side effect of reading a page they were already allowed to open. A required-reason field makes sense for the explicit `POST /api/reveal` action a person chooses to call, not for this one |
| 2026-10-18 | `respond_review_note` now refuses an already-resolved note with a 409, carrying the current (redacted) note -- reversing the decision two rows up, made the same day | User's call, after weighing it directly: a resolved note is a closed decision, and letting responses keep landing on it with no state transition would make "resolved" meaningless as a signal and the audit trail confusing to read back later. 409 fits better than 403 (not a permission problem) or 422 (not a malformed request) -- the entity's own state conflicts with what the action means, the same category as a stale revision, just not caused by one |
| 2026-10-18 | New `ActionConflict(detail, current)` in `actions/errors.py`, kept distinct from `proofline.db.repository.StaleRevision` even though both map to 409 and carry `current` | `StaleRevision` means "the revision you acted on isn't current anymore"; `ActionConflict` means "the entity's current state makes this action meaningless, independent of which revision you had." Collapsing them into one exception would lose that distinction for any future caller that needs to tell the two apart (e.g. to decide whether retrying with a fresh revision would ever help) |
| 2026-10-18 | `app.py`'s two 409 handlers share a new `_conflict_response(request, detail, current)` helper instead of each redacting/building the body inline | The only difference between `StaleRevision`'s 409 and `ActionConflict`'s 409 is which string explains *why*; duplicating the redact-and-build-body logic for a second exception type would've been copying six lines verbatim, not writing something genuinely different |
| 2026-10-18 | Step 5: `review_notes.body` is now stored on the current-state row (migration `c1a53e8f9201`), holding the *latest* text (opening body, or latest response's body) | User's explicit instruction for Step 5, which partially reverses the Step 4 decision that a note's text lives only in events -- it reverses only the "own text is event-only" half; the thread of every response still lives only in `review_note_responded` events, never as rows, because a growing log of what people said is still "what people did," not a point-in-time snapshot |
| 2026-10-18 | Cases/proposals/decisions use the same generated-id convention as review notes (`case-{uuid4()}`, `proposal-{uuid4()}`, `decision-{uuid4()}`), not a short mnemonic like the packet's `D01`/`ev-0012` | Workpaper-native ids should look visibly different from packet references, and the existing `note-{uuid4()}` convention from Step 4 already establishes the pattern |
| 2026-10-18 | A `case_opened` event's payload carries the full finding (`CheckResult.model_dump(mode="json")`, converted via the existing `prepare_payload_for_storage`) for a check-origin case, or every field the preparer supplied for a hand-opened one, rather than just a few identifying fields | Rebuild (`db/rebuild.py`) must reconstruct the exact same `Case` row from the event alone, without rerunning the check that produced it -- a check's logic can change later, but CONTRACTS.md Storage requires an old event to stay replayable forever |
| 2026-10-18 | `case_proposal_submitted`, `case_returned`, `case_approved`, `case_partner_approved` and `case_partner_returned` events all carry the proposal's or decision's own generated id (`proposal_id`/`decision_id`) in their payload | Without it, `rebuild_current_state` would have to invent a new id for the replayed `CaseProposal`/`CaseDecision` row, which would never match the id the live write actually used -- caught by extending `test_rebuild.py` with a full case-lifecycle scenario before trusting I5 held for cases at all |
| 2026-10-18 | `proofline/db/repository.apply_revision_cas` now reads the model's primary-key column via `sqlalchemy.inspect(model).primary_key` instead of assuming a column literally named `id` | `Case`'s primary key is `case_id`, not `id` -- the hardcoded `model.id == pk_value` raised `AttributeError` the moment any case transition test ran; caught immediately by the new C1 transition test suite, not a case this project can afford to find later |
| 2026-10-18 | `sync_cases_from_findings` upserts by root-cause key and clears a check-origin case whose finding stops firing, but only from `open`/`investigating` -- a case already `in_review`, `awaiting_partner`, `waiting_on_client`, `resolved` or `cleared` is left alone even if its finding stops firing in that same sync | A finding that stops firing because someone's proposed fix hasn't landed in the packet yet (it can't, since the engine/packet never changes from this app) shouldn't silently vanish a case mid-review; only an untouched, still-open investigation is safe to auto-clear |
| 2026-10-18 | A new synthetic `"system"` role (`security/actors.py`), never built from the packet and never returned by `load_actors` | CONTRACTS.md C1 names "System" as the actor for the `clear` transition and part of `reopen`; the existing synthetic-actor pattern (the AI assistant, Step 4) already established that not every actor needs to come from packet data |
| 2026-10-18 | `submit_proposal`, `pick_up` and `ask_client` are preparer-only (not any staff role), and `return`/`approve` are restricted to reviewer/partner/quality_reviewer -- stricter than CONTRACTS.md C1's bare "Preparer" / "A reviewer who didn't propose it" might suggest for a firm with multiple preparers | Matches the firm's actual staff roles (Priya is the only preparer; Daniel, Helen and Sam hold reviewer-ish roles) and keeps `check_permission`'s one `if/elif` chain legible; the "nobody reviews their own work" guard inside `return`/`approve` themselves stays as independent defense-in-depth even though the role split makes it currently unreachable through the real permission chain |
| 2026-10-18 | `reopen` is allowed for `system`, `reviewer`, `partner` and `quality_reviewer` (the same set as `return`/`approve`), not only "reviewer" as CONTRACTS.md C1's "System or reviewer" literally reads | A partner or quality reviewer is a reviewer in every other C1 row (`return`, `approve`); excluding them only for `reopen` would be an arbitrary gap with no stated reason, not a deliberate narrowing |
| 2026-10-18 | `open_case_by_hand` (a case opened by a preparer, reviewer, document gap, etc.) is staff-only, even when `origin="client"` | A client in this prototype never reaches the firm's case-opening screen directly; a client-origin case is always opened by a staff member *about* something the client said, not self-served. Revisit once Step 9's client workspace exists |
| 2026-10-18 | The queue's severity group order is `blocks_filing, tax_amount, penalty_risk, info`, matching docs/UX.md's S1 spec exactly, not `CheckResult.Severity`'s declared literal order (`blocks_filing, penalty_risk, tax_amount, info`) | UX.md is the source of truth for screen layout per CLAUDE.md's Part 0 instructions; the two orderings happen to differ and the display order is the one that matters for S1 |
| 2026-10-18 | A case's `approve` tax-effect threshold check (over/under $1,000, routing to `awaiting_partner` vs `resolved`) compares the case's own stored `tax_effect_federal`/`tax_effect_california` (set once, from the originating finding or hand-entry) -- it does not recompute via C3's adjustment-aware calculation | C3's full adjustment-overlay calculation (`analysis/calculation.py`) is Step 7 work; Step 5's case lifecycle only needs the tax effect already computed by the check (or stated by whoever opened the case by hand) to decide the partner-threshold branch, matching A1's scenario exactly (the RSU case's estimate is fixed at detection time) |
| 2026-10-18 | "Needs me" tab filtering (S1): preparer = cases `open` or `investigating`-and-assigned-to-me; reviewer/quality_reviewer = `in_review` not proposed by me; partner = `awaiting_partner`; every other role defaults to open-ish cases assigned to them | docs/UX.md gives the preparer/reviewer/partner rules in words ("open and returned cases assigned to me", etc.) with some room for interpretation on exactly which states count as "returned"; this reading keeps a preparer's queue to cases that are actually theirs to pick up or rework, and leaves the fallback narrow (assigned-to-me) rather than guessing at an undefined role's intent |
| 2026-10-18 | Web: no SWR/react-query (CLAUDE.md only allows `openapi-typescript` and Playwright-via-npx as new dependencies), so every screen fetches with plain `fetch` inside `useEffect` plus manual loading/error state | The alternative is hand-rolling an in-house fetch library, which is a bigger and riskier undertaking than the two sanctioned dependencies already cover for a prototype at this scope |
